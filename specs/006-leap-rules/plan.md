# Implementation Plan: Leap Rules

**Branch**: `design/006-leap-rules` (design), `build/006-leap-rules` (build) | **Date**: 2026-11-16 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/006-leap-rules/spec.md` (approved by the owner, 2026-11-15, re-approved after the split)

## Summary

`uni-calendar` gains leap rules on the era's unit. Each rule's condition is checked, its period worked out and, for one rule period of years, evaluated with spec 005's `uni-expr`; the engine refuses anything that could fail later. Checking builds one cycle table (each year's variant of member lengths and the start of each year in the cycle), so both conversion directions find any year by one division and one binary search, however far it is from the epoch (the supercycle strategy). Units above the era's unit are numbered by their count of years. Calendars without rules use the same path with a one-year cycle. Details are in [research.md](research.md).

## Technical Context

**Language/Version**: Rust 1.99.1 (pinned), edition 2024.

**Primary Dependencies**: `uni-time` (as before) and now `uni-expr` (spec 005), both workspace crates. Dev-only: `proptest`, `num-bigint`, `num-rational` (as in spec 004). The Gregorian fixture is generated by a committed Python script using only the standard library (`datetime`, `calendar`).

**Storage**: N/A (engine only; spec Assumptions).

**Testing**: `cargo test -p uni-calendar`: hand-worked tests for every acceptance scenario (Aster and Tessel with rules), property tests (10,000 cases each) for round trips and against a year-by-year reference, the Gregorian-shaped comparison with Python's `datetime` for years 1 to 4000, and a timing check run by hand (research R8).

**Target Platform**: any; tested on Windows and Linux in CI.

**Project Type**: library crate.

**Performance Goals**: under 10 µs per conversion with leap rules, near the epoch and 100,000 years away (SC-004).

**Constraints**: no floating point (exact crate); no panics; every expression failure found when the calendar is checked (FR-006); rule period at most 100,000 instances (research R3).

**Scale/Scope**: about 1,500 lines: roughly 550 of engine changes (rule checking, the cycle table, conversion and `units_per` through it, `era_instance`, errors), 850 of tests and 100 of fixture generator, test calendars and existing tests gaining `rules: vec![]`; plus a generated fixture of about 180 KB that isn't reviewed line by line. One build PR; see principle VIII below.
